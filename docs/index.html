Models as a Service auth path

Red Hat Connectivity Link attaches one AuthPolicy to Gateway maas-default-gateway. Every child HTTPRoute (/maas-api and the simulator) is covered. The CRD API is still kuadrant.io/v1; the product name is Connectivity Link. Source: docs/_diagram-authpolicy.html.

Quick commands

Resolve the Route from the cluster you are logged into. OpenTLC FQDNs rotate.

ROUTE=https://$(oc get route inference -n ocp-datalake -o jsonpath='{.spec.host}')
curl -sk -H 'Content-Type: application/json' \
  -d '{"tenure":12,"charges":70,"support_tickets":3}' \
  "$ROUTE/predict"

MAAS_URL=https://maas.$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
TOKEN=$(oc whoami -t)
API_KEY=$(curl -sk -X POST "$MAAS_URL/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"poc","subscription":"simulator-free","expiresIn":"1h"}' \
  | python -c "import json,sys; print(json.load(sys.stdin).get('key',''))")
curl -sk "$MAAS_URL/v1/chat/completions" \
  -H "Authorization: Bearer $API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"publishers/llm/models/facebook/opt-125m","messages":[{"role":"user","content":"Hello"}],"max_tokens":16}'

Databricks compatibility

Today: high conceptual fit, low technical fit. The flow (registry → promotion → serving under cluster policy) is modeled well. The artifact contract is not MLflow: it is a coefficients JSON, not an MLmodel + model.pkl directory. Do not point a production registry at this PoC.

FitWhat lands
HighLinear model exported by hand (coef_ / intercept_) into this JSON. That is churn-score v1, not “fetch the model from the registry”.
Mediumsklearn / XGBoost / LightGBM: change the ServingRuntime (MLServer + mlflow, or ONNX + OVMS/Triton). Do not patch server.py. Watch pickle vs UBI 3.12.
LowSpark ML, Feature Store / Unity Catalog at inference, DBFS paths or UC volumes.

Artifact contract and model-type fit only. For the real pull path and product mapping, see Databricks bridge below or the README.

Databricks bridge

OpenShift never enters the Databricks workspace. In a real integration the cluster pulls a versioned artifact, validates it, registers it, and serves it under the same policies as the rest of the workloads. Databricks stays the training and catalog plane; OpenShift is deployment, identity, and inference.

Bridge vs replace: Bridge — Databricks trains and registers; OpenShift pulls, governs, and serves (this document). Replace — RHOAI + ODF + Pipelines + Feast/Iceberg on OpenShift; you lose UC and the managed Spark runtime. This PoC demonstrates the bridge story.
